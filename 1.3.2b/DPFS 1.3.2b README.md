# DPFS
**Version 1.3.2b**

DPFS (Delta Pseudo-hierarchical File System) is a fast and comprehensive file system. It can be accessed via the Delta Kernel syscall interface. It stores flat file and directory paths across 4 lists and the entire filesystem is also exportable. 

As of the current version, mode has not been utilized yet (and might never be).

## Versioning
Different versions of DPFS might not be compatible with each other. To check the current version, access the global variable `fs.version`. A list of compatible DPFS versions to your version can be found in the global list `fs.compatible_versions`. These variables should not be modified unless you really need to. DPFS also automatically detects incompatible versions in a encoded filesystem savecode and returns an error.

## Usage
You should use DPFS as an independent sprite and use it via the syscall interface to ensure upgradability
DPFS can be accessed via 2 main methods: Intra-sprite and inter-sprite. DPFS can be accessed through the `external_use_funs_template.send_syscall` function in the sprite for intra-sprite usage. Inter-sprite usage is the default, and is achieved by using the Delta Kernel syscall interface. The template function to access DPFS for external sprites is the same for above, except you should drag it to another sprite and rename `external_use_funs_template.send_syscall` your sprite name.

### Calling DPFS (via both methods)
In both abovementioned methods, calling DPFS requires a function functionwise similar or identical to `external_use_funs_template.send_syscall`, and the usage of this function in both cases is identical. 

DPFS calls contain 6 arguments: `op`, `val0`, `val1`, `val2`, `val3`, `val4`. Each argument is supplied to the corresponding ones in filesystem functions. A request is added to the request queue and the requester sprite/function records ite queue number in `_app.kernel_syscall_queue_idx`. It will be used to access the results of calls. This number should only be reset when DPFS is reinitialized. As mentioned, the template script for to send a request is in `external_use_funs_template.send_syscall`. Whenever the filesystem completes a queued operation it sends kernel.syscall.return together with the queue index of the operation completed. 

### Functions
DPFS has many functions ("`op`s") that you can use and below is a table containing the usage guide for al of them. Every function will return an errno, 0 for a successful operation. DPFS uses the errno symbols for simplicity. A list of errnos and what they stand for can be found at https://www.chromium.org/chromium-os/developer-library/reference/linux-constants/errnos/. Some functions can also return values. These values and the operation's error symbols are stored in `kernel.return.val<val_num>` and can be accessed using the queue number generated by the requester. There are also special functions such as `READDIR` that outputs to `kernel.return.list0`. If a function does not return anything, the index of its output in the return lists will be blank.

In the table below, arguments in square brackets (`[]`) are optional.

| Function Name | Arguments | Usage | Returned Values |
| :--- | :--- | :--- | :--- |
| CREATE | `path`, `type`, `data`, `mode` | Creates a file or directory with path `path`, file type `type` or use `DIR`, file data as `data` (argument should be empty for directories) and mode as `mode`. |
| UNLINK | `path` | Removes a file at `path`. |
| RMDIR | `path`, `[ignore_empty]` | Removes an empty directory at `path`. If `[ignore_empty]` is true, this function will be able to remove non-empty directories. |
| RENAME | `path`, `new_path` | Rename/move a file or directory at `path` to `new_path`. Renaming a directory also renames all its children accordingly. |
| READ |  `path` | Reads the data of the file at `path`. Returns the data of the file, `data` | `data` |
| READDIR | `path` | Gets all the directory and files in a directory `path`. The output will be stored in `kernel.return.list0`. The range of output of the function in the list is from `range_start` to `range_end`. | stores to `kernel.return.list0`. `range_start`, `range_end`
| STAT | `path` | Returns the statistics about the file or directory at `path`. If the item is a file, the function outputs the index of the file in FS.PATHS as `path_idx`, type of the file as `file_type`, the length of the file's data in `data_size`, length of path at `path_size` and mode in `mode`. If `path` is a directory, the function will return the index of the directory in FS.PATHS as `path_idx`, `DIR` in `file_type`, the total length of all the nested files in the directory in `data_size`, length of all nested files and directories' path at `path_size` and the mode in `mode`. | `path_idx`, `file_type`, `data_size`, `path_size`, `mode` |
| EXPORT | `path` | Exports the target directory `path` into `exported_dir`. | `exported_dir` |
| IMPORT | `encoded_dir`, `[replace_dir]`, `[replace_data]`, `[replace_mode]` | Imports the encoded directory in `encoded_dir`. If `[replace_dir]` is true, the entire target directory with the name defined in `encoded_dir`, if it exists, will be wiped and replaced entirely with the contents of the savecode. `[replace_data]` and `[replace_mode]` when true, replaces different data and mode of files with the ones in the encoded directory respectively. |

# Modification
Only read this section if you wish to modify DPFS.

## Versions
There are 2 main types of releases - stable and betas. Stable releases are releases that are tested and no major bugs are found. Beta releases are experimental and may contain bugs.
DPFS does not contain a version management system. You are highly encouraged to choose the latest stable relase of DPFS for your projects, as to implement a new version you will have to perform your modifications again. Refer to the [Releases](#releases) section for a list of DPFS releases.

### Releases
The "General Compatibility" section indicates the versions that version of DPFS is compatible with. This includes interchangeable filesystem storage and savecodes. For a more specific compatibility information, check each of the release's READMEs on GitHub (if available).
The source of the releases are the locations where the modification-oriented versions of each release are posted. "GitHub Repository" means that the version's code is available in the official GitHub repository. "Not Readily Modifiable" means that the version has been altered in some way and released in a project, but the base code has not been posted. "Not Public" means that no code of this version whether modified or not is publically available.

There are tools to upgrade older DPFS filesystems to new ones on, altohugh it may not be available for all releases.

## Modification of Syscall Interface
The Delta Kernel Syscall Interface can be modified or removed to suit your usage. You should remove it if you plan on accessing the filesystem in the same sprite where the code is, although this is adviced against.
